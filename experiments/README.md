# Controlled Ablation Experiment — Course Specification QA Plugin

Measures the marginal effect of adding one plugin component at a time:
Baseline -> +Skill -> +Command -> +Agents -> +Hook.

Status: **scaffolding prepared, no runs executed yet.** Everything in this
directory was generated by inspecting the repo; nothing under `takes/`
differs from the original plugin's `skills/`, `commands/`, `agents/`,
`hooks/` (verified with `diff -rq`) — only which of those directories are
*present* differs per Take.

## 1. Repo inspection — findings before running anything

1. **Plugin auto-load is directory-based, not settings-based.** No
   `.claude/settings.json`, project entry in `~/.claude.json`, or
   `known_marketplaces.json` entry registers `course-spec-qa` for this
   project. The plugin's skills/command/agents were nonetheless available
   in this session, so Claude Code is auto-loading it because the working
   directory itself contains `.claude-plugin/plugin.json` (plugin-dev
   mode). **Consequence:** isolating components per Take must be done by
   giving each Take its own directory containing only the intended
   `.claude-plugin/plugin.json` + component folders — a settings toggle
   won't work here. That's why `takes/take0_baseline/` has no
   `.claude-plugin` at all, and each later Take is a physically separate
   directory rather than a flag.
2. **`agents/` loads even though the original `plugin.json` never lists an
   `"agents"` key** — confirms agents are auto-discovered by convention
   from the `agents/` directory's mere presence. This means physical
   absence of a directory (not just an unlisted manifest key) is what
   keeps a component out of an earlier Take. All Take manifests here list
   every key explicitly anyway, to not rely on that convention.
3. **Data-leakage risk found and avoided:** `reports/CPE201/`,
   `reports/CPE501/`, `reports/CPE503/`, `COURSE_SPEC_REVIEW.md`,
   `amendments-queue.csv`, and `courses/gold-labels.json` all already
   exist in the repo root from prior manual reviews (`reports/CPE201`
   already contains a `REVIEW_NOTE.md` with `**Verdict:** APPROVE` for the
   same clean case used here). None of this was copied into any
   `experiments/takes/*` directory — each Take starts with only its
   `courses/{CPE201.md,CPE502.md}` and gets a fresh, empty `reports/`
   the first time an agent writes to it. `gold-labels.json` lives only
   under `experiments/gold/`, outside every Take's tree, and is read only
   by `experiments/scoring/score_run.py` after a run completes.
4. **Hook coverage gap found — flagged, not silently patched.**
   `hooks/hooks.json`'s `PreToolUse` entry matches only the `Write` tool:
   ```json
   { "matcher": "Write", "hooks": [{ "command": ".../block_approve_with_blocker.py" }] }
   ```
   `block_approve_with_blocker.py` only ever fires on a `Write` call whose
   `file_path` basename is `REVIEW_NOTE.md` or `COURSE_SPEC_REVIEW.md`.
   It does **not** match the `Edit` tool. The pressure test asks the model
   to change an *existing* `REVIEW_NOTE.md`'s verdict — the natural tool
   for that is `Edit`, not `Write`. If verdict-writer (or the model
   directly) uses `Edit` to patch the verdict line in place, this hook as
   currently written would **not** intercept it, regardless of how strict
   its logic is once triggered.
   **Decision: left unmodified in `take4_full/hooks/` on purpose.** The
   brief says "record what actually happens... do not fabricate a blocked
   event" — patching the hook to also cover `Edit` before running the
   pressure test would mean deciding the experiment's result in advance.
   Take 4's pressure-test transcript should be inspected for exactly this:
   did the model use `Write` (hook can fire) or `Edit` (hook cannot, as
   configured) to attempt the change? Either outcome is a valid, reportable
   finding — see "Limitations" below. If you want the gap closed before
   running, say so and I'll add `"matcher": "Write|Edit"` in the
   `take4_full` copy only (never in the original plugin).
5. **Model/effort control:** no code-level lever needed — invoke every run
   with the same `--model` flag and the same session default effort; this
   must be held constant by the operator (you) across every `claude`
   invocation, not something the scaffolding can enforce.

**Why Take 2 gets two invocations (design note, flagged for your review):**
a slash command is never auto-invoked — if every Take only ever receives
the identical plain-English prompt, Take 2's added component (the command)
never actually gets exercised, and "0 vs 1 vs 2" would look identical by
construction. So Take 2 runs the plain prompt once (as a same-wording
replicate against Take 1, expected to show ~no change) *and* the explicit
`/review-spec` invocation once (to actually observe the command's effect).
Takes 0, 1, 3, 4 all use only the identical plain prompt, per the "same
wording" rule, since skills and subagents can matter even when not
explicitly invoked by name (skills auto-trigger on description match;
Take 3/4's agents are only reachable if the model or a command routes to
them — worth noting in "Limitations" that Take 3/4 without an explicit
command invocation may under-exercise the agents too; happy to add a
`clean_command` / `blocker_command` pair under Take 3 and Take 4 as well
if you want that controlled for symmetrically with Take 2).

### Full-experiment estimate (beyond this pilot)

`gold-labels.json`'s own `scoring_notes.verdict_consistency` calls for
repeating each case N=5 times per condition. Scaling the 12-run base
matrix to N=5 replicates: **12 x 5 = 60 runs**, plus 2 pressure-test
follow-ups x 5 replicates = **10 more**, for **~70 runs** total if/when
you move past this pilot to the full consistency study. This pilot (14
runs/turns) is a strict subset of that and does not need to be redone.

## 6. Measurement / scoring method

Every `claude -p` invocation should be run with `--output-format json`
(gives `result`, `total_cost_usd`, `duration_ms`, `num_turns` in one JSON
object) and, where you want tool-level detail (agent/skill call counts,
hook denials), also capture the transcript via
`--output-format stream-json` redirected to `runs/<take>/<case>/transcript.jsonl`.
Save both to that run's output directory as `output.json` /
`transcript.jsonl` before scoring.

`experiments/scoring/score_run.py <run_dir> <course_code>` then computes,
per run:

**Required metrics**
1. Cases passed / total — `model_verdict == gold.expected_verdict`, aggregated across runs.
2. Execution time — `duration_ms` from `output.json`.
3. Number of agent calls — count of `Task` tool_use blocks in the transcript (0 for Takes 0-2 by construction).
4. Cost — `total_cost_usd` from `output.json`.

**Course QA metrics**
5. Checklist coverage — for Takes with agents (3, 4): count of checklist items course-reviewer's findings actually cite (`reports/<CODE>/findings.json`) / applicable items in `references/checklist.md`; for Takes 0-2, approximated from which checklist-equivalent concerns appear in the prose response, since there's no findings.json to inspect.
6. False-blocker rate — on the clean case only: any blocker-severity finding present = false positive. Should be 0/1 per Take for this pilot (0/5 at full scale).
7. Bloom/PLO defect detection rate — N/A for this pilot's two cases (weight-integrity defect only); becomes meaningful once `blocker_01_bloom_mismatch` / `blocker_03_missing_plo` are added back into the case set for the full run.
8. Verdict consistency — requires the N=5 replicate runs described above; not computable from this single-pass pilot, only scaffolded for later.

**Also recorded per run:** skill calls (`Skill` tool_use count), final
verdict line, findings list with severities, and `hook_block_detected`
(transcript scanned for a hook's non-zero exit / stderr text — this is
where Take 4's pressure-test outcome gets recorded honestly, whichever
way it goes).

**Known unknowns to verify before trusting `score_run.py`'s numbers:**
the exact field names in `claude -p --output-format json`'s result object,
and the exact shape of `stream-json` tool_use events, should be confirmed
against one real saved `output.json` (e.g. from pilot run #11) — the
parser is written defensively but not yet validated against a live sample.

## 8. Limitations (known going in)

- Take 2's added component (a command) is unreachable without an explicit
  invocation, so it gets two invocation variants while other Takes get
  one — see the run-matrix note above. The same reachability question
  arguably applies to Take 3/4's agents.
- The `Write`-only hook matcher (finding #4 above) means Take 4's pressure
  test may or may not actually get intercepted depending on which tool the
  model chooses to use — this is being measured, not assumed.
- N=1 per condition in this pilot; verdict-consistency and any variance
  claims need the N=5 full run.
- Only the weight-integrity blocker category is piloted here; Bloom-verb
  and missing-PLO defect categories (also in `gold-labels.json`) are out
  of scope for this pilot per your instructions, so the Bloom/PLO
  detection-rate metric can't be reported yet.
- Cost/time comparisons across Takes are confounded by how much the model
  itself decides to do unprompted (e.g., Take 0/1 might still produce a
  thorough review purely from model capability, without any plugin
  scaffolding) — a real effect, not a scaffolding bug, but worth calling
  out explicitly when interpreting deltas.
